# Notifications use domain signals without a user-facing inbox

Food Tracker notifications use **Notification Signals** that may appear as device notifications, in-app indicators, or both, but the first version will not create a user-facing notification inbox. In-app indicators are derived from unresolved domain state such as friend requests, pending tasting invites, shareable tasting invite windows, and active Bills where the signed-in user owes money; remote device notifications are reserved for tasting invites, Bill owed-money events, explicit weekly-limited Bill payment reminders, and monthly friends activity digests.

We chose this over a notification inbox because each signal already has a natural destination screen, while an inbox would add read/unread state, retention, deletion, and deep-link consistency without clear first-version value. The backend will still keep a minimal, backend-only **Notification Delivery Log** for remote notification deduplication, weekly reminder limits, monthly digest send tracking, and delivery debugging; it must not store notification body text or push tokens. User-scheduled visit reminders are one-time local device notifications from the Add tab quick reminder action, separate from remote notification preferences.
